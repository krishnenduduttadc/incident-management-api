# REST API – FRONTEND INTEGRATION GUIDE

Base URL:
http://localhost:5000/api

Content-Type:
application/json

============================================================
0. COMMON SETUP
============================================================

All examples use curl. For convenience, define:

```bash
BASE_URL="http://localhost:5000/api"
```

For requests with JSON bodies, use:

```bash
-H "Content-Type: application/json"
```

Replace IDs such as `1`, `2`, and `3` with actual database IDs returned by the APIs.

============================================================
1. HEALTH API
============================================================

1.1 Check application and database health

Method: GET
Endpoint: /health

Description:
Checks whether the Flask application and PostgreSQL database are available.

```bash
curl -X GET "$BASE_URL/health"
```

============================================================
2. USERS API
============================================================

2.1 Create user

Method: POST
Endpoint: /users

Description:
Creates a new user.

```bash
curl -X POST "$BASE_URL/users" \
  -H "Content-Type: application/json" \
  -d '{
    "userid": "user001",
    "username": "John Smith",
    "email": "john@example.com",
    "active": true
  }'
```

2.2 Get all users

Method: GET
Endpoint: /users

Description:
Returns a paginated list of users.

```bash
curl -X GET "$BASE_URL/users"
```

With pagination:

```bash
curl -X GET "$BASE_URL/users?page=1&per_page=20"
```

2.3 Get user by ID

Method: GET
Endpoint: /users/{user_id}

```bash
curl -X GET "$BASE_URL/users/1"
```

2.4 Update user

Method: PUT
Endpoint: /users/{user_id}

Description:
Updates the supplied fields. This endpoint supports partial updates.

```bash
curl -X PUT "$BASE_URL/users/1" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "John Updated",
    "email": "john.updated@example.com",
    "active": true
  }'
```

2.5 Delete user

Method: DELETE
Endpoint: /users/{user_id}

```bash
curl -X DELETE "$BASE_URL/users/1"
```

Note:
Deletion may return HTTP 409 if the user is referenced by incidents, assignments or history.

6. INCIDENT API
============================================================

6.1 Create incident

Method: POST
Endpoint: /incidents

Description:
Creates an incident, creates its initial mapping and records a CREATED event in incident history.

Required fields:
- incidentsubject
- created_by
- initial_status_id

```bash
curl -X POST "$BASE_URL/incidents" \
  -H "Content-Type: application/json" \
  -d '{
    "incidentsubject": "Production server is down",
    "incidentdesc": "Application server is not responding",
    "created_by": 1,
    "incident_type_id": 1,
    "priority": "HIGH",
    "initial_status_id": 1
  }'
```

Priority values:

LOW
MEDIUM
HIGH
CRITICAL

6.2 Get all incidents

Method: GET
Endpoint: /incidents

Description:
Returns a paginated list of incidents, including their mapping information.

```bash
curl -X GET "$BASE_URL/incidents"
```

With pagination:

```bash
curl -X GET "$BASE_URL/incidents?page=1&per_page=20"
```

Filter by priority:

```bash
curl -X GET "$BASE_URL/incidents?priority=HIGH"
```

6.3 Get incident by ID

Method: GET
Endpoint: /incidents/{incident_id}

```bash
curl -X GET "$BASE_URL/incidents/1"
```

6.4 Update incident

Method: PUT
Endpoint: /incidents/{incident_id}

Description:
Updates incident details and records an UPDATED event in incident history.

A valid actor is required.

```bash
curl -X PUT "$BASE_URL/incidents/1" \
  -H "Content-Type: application/json" \
  -d '{
    "incidentsubject": "Production database server is down",
    "incidentdesc": "Database connection is failing",
    "priority": "CRITICAL",
    "changed_by_user_id": 1,
    "comments": "Updated after initial investigation"
  }'
```

Other supported update fields:
- incidentsubject
- incidentdesc
- incident_type_id
- priority

6.5 Delete incident

Method: DELETE
Endpoint: /incidents/{incident_id}

```bash
curl -X DELETE "$BASE_URL/incidents/1"
```

Note:
An incident with an associated mapping or history cannot be physically deleted by this API. The API returns HTTP 409. Consider implementing a soft-delete or archive operation for production.

Method: DELETE

```bash

  -H "Content-Type: application/json" \
  -d '{
    "changed_by_vendor_id": 1,
    "comments": "Vendor requested removal"
  }'
```

8. INCIDENT STATUS API
============================================================

8.1 Change incident status

Method: PATCH
Endpoint: /incidents/{incident_id}/status

Description:
Changes the incident's current status and records a STATUS_CHANGED history event.

Required field:
- status_code

User actor example:

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "IN_PROGRESS",
    "changed_by_user_id": 1,
    "comments": "Investigation started"
  }'
```

Move incident to ON_HOLD:

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "ON_HOLD",
    "changed_by_user_id": 1,
    "comments": "Waiting for replacement hardware"
  }'
```

Close incident:

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "CLOSED",
    "changed_by_user_id": 1,
    "comments": "Issue resolved successfully"
  }'
```

Reopen incident:

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "REOPENED",
    "changed_by_user_id": 1,
    "comments": "Issue occurred again"
  }'
```

Vendor actor example:

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "IN_PROGRESS",
    "changed_by_vendor_id": 1,
    "comments": "Vendor started troubleshooting"
  }'
```

Note:
The current API validates that the status exists, but does not yet enforce a status-transition state machine.

11. COMPLETE INCIDENT LIFECYCLE – EXAMPLE
============================================================

The following sequence demonstrates a typical incident workflow.

Step 1: Create incident

```bash
curl -X POST "$BASE_URL/incidents" \
  -H "Content-Type: application/json" \
  -d '{
    "incidentsubject": "Email service unavailable",
    "incidentdesc": "Users cannot send or receive emails",
    "created_by": 1,
    "incident_type_id": 1,
    "priority": "HIGH",
    "initial_status_id": 1
  }'
```

Step 2: Assign incident to a user

```bash
curl -X PUT "$BASE_URL/incidents/1/assignment" \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": 2,
    "assigned_by": 1
  }'
```

Step 3: Change status to IN_PROGRESS

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "IN_PROGRESS",
    "changed_by_user_id": 2,
    "comments": "Investigating email service"
  }'
```

Step 4: Reassign incident to vendor

```bash
curl -X PUT "$BASE_URL/incidents/1/assignment" \
  -H "Content-Type: application/json" \
  -d '{
    "vendor_id": 1,
    "assigned_by": 1
  }'
```

Step 5: Vendor updates status

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "IN_PROGRESS",
    "changed_by_vendor_id": 1,
    "comments": "Vendor is troubleshooting"
  }'
```

Step 6: Close incident

```bash
curl -X PATCH "$BASE_URL/incidents/1/status" \
  -H "Content-Type: application/json" \
  -d '{
    "status_code": "CLOSED",
    "changed_by_vendor_id": 1,
    "comments": "Email service restored"
  }'
```

Step 7: Retrieve final incident

```bash
curl -X GET "$BASE_URL/incidents/1"
```

Step 8: Retrieve complete history

```bash
curl -X GET "$BASE_URL/incidents/1/history"
```

12. HTTP RESPONSE CODES
============================================================

200 OK
Request completed successfully.

201 Created
A new record was created successfully.

400 Bad Request
Invalid request data or missing required fields.

404 Not Found
Requested record or resource does not exist.

409 Conflict
Duplicate data, foreign-key constraint violation, or a record that cannot be deleted.

500 Internal Server Error
Unexpected server-side error.

============================================================
13. IMPORTANT FRONTEND INTEGRATION NOTES
============================================================

1. Always send JSON with Content-Type: application/json.

2. Use IDs returned by the APIs. Do not assume IDs are sequential or hardcode them.

3. Load reference data for dropdowns:
   - GET /users
   - GET /vendors
   - GET /incident-types
   - GET /incident-statuses

4. Incident creation requires:
   - created_by
   - initial_status_id
   - incidentsubject

5. Assignment requires exactly one of:
   - user_id
   - vendor_id

6. Assignment also requires assigned_by.

7. Incident update, status change and unassignment require an actor:
   - changed_by_user_id
   - OR changed_by_vendor_id

8. Incident history is read-only for frontend users. History is automatically generated by the backend.

9. Mapping changes should be performed through assignment and status endpoints, not direct database updates.

10. The current API examples pass actor IDs in request bodies for development/testing. In production, these actor IDs must come from the authenticated user's server-side identity. Do not trust actor IDs supplied by the browser.

11. The current API does not yet provide authentication/authorization, filtering by user/vendor, sorting, or a status-transition state machine. These should be addressed before production deployment.
